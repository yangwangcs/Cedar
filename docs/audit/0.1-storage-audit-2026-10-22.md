## 0. 结论摘要

三处**契约没有闭环**，这是绝大多数问题的根因：

1. **MemTable 的排序契约 ≠ SST 的键序契约**：跳表按 `entity_id, column_id, target_id, timestamp DESC` 排序（`versioned_skiplist_lockfree.cc:112-125`），而 `CedarKey::Compare` 是 `entity_id, entity_type, column_id, target_id, ~timestamp, sequence, flags`（`cedar_key.h:389-420`）。`entity_type`、`sequence` 不参与跳表排序，导致同 entity 的 Vertex/EdgeOut/EdgeIn 交错，且版本链会断。
2. **列式文件的 zone 是"按 block 编码"的，文件格式却是"按 zone 连续拼接"的**：读端把整条 zone 流当成一个编码单元解码。target 区每块都带一个编码类型字节（`zone_encoder.cc:599`），多 block 文件从第 2 块起 target_id 全部错位。
3. **Compaction 只合并部分输入，却删除全部输入**：`DoZoneCompaction` 只把 `task.input_files` 传给 `MergeZones`，随后把 `task.overlapping_files` 从下层删掉（`size_tiered_compaction.cc:685, 743-750`）——下层文件内容直接丢失。

另外两个系统级缺口：

- **没有 WAL 重放**：`WalReader`（`wal.h:249`）存在但全仓库没有恢复调用；`Database::Recover()` 只打开存储（`database.cc:442-486`），注释里的 "fast recovery 跳过 WAL 重放" 实际上无重放可跳过。
- **Flush 丢弃 tombstone**：`FlushMemTable` 明确跳过 `descriptor.IsTombstone()` 的条目（`lsm_engine.cc:1085-1092`），删除只活在 memtable 里，一落盘就"复活"。

P0（数据丢失 / 损坏 / 不可恢复）11 条、P1（并发/恢复下结果错误）30+ 条、P2（性能/可扩展）13 条、P3（可维护）若干。第 8、9、10 节是三轮独立子审计的交叉复核补充；其中 9.1/9.2/9.3、10.1 是后发现的 P0，10.1（单行 SST 时间戳解码为空）影响面最大。

## 1. 版本链跳表（LockFreeVSL / VSLMemTable）

### 1.1 [P0][已确认] Insert 完全不是无锁的，却被并发事务共享

`src/storage/versioned_skiplist_lockfree.cc:97-165`

```cpp
// 单线程 Insert
bool LockFreeVSL::Insert(...) {
  ...
  for (int i = 0; i < height; i++) {
    preds[i]->SetNext(i, new_node);   // 普通 store，非 CAS
  }
```

- 注释自己写了"单线程 Insert"；`SetNext` 是 `std::atomic::store`（`LFNode::SetNext`），没有 CAS 重试。
- 但 `OCCTransaction` 在 `Commit` 里直接写共享 memtable（`occ_transaction.cc:614`），`mutex_` 是**每个事务自己的**，不是 memtable 的；`LsmEngine::BeginTransaction` 把同一个 `mem_.get()` 交给所有事务（`lsm_engine.cc:1037-1043`）。
- 两个事务同时 Commit 时：后写者用已失效的 `preds[]` 覆盖前写者的 next 指针，节点丢失；并发 CAS 无重试还可能形成环或断链。名字叫 LockFree，实现是单线程链表头插 + 指针覆盖。

**影响**：任意并发写都可能丢节点、链表损坏、`Traverse`/flush 崩溃或死循环。**修法**：要么 memtable 写入串行化（每 memtable 一把写锁，最省事），要么真正实现 CAS 插入 + 内存回收（hazard pointer/epoch）。

### 1.2 [P1][已确认] 版本链只连 older，不连 newer；newer 永远为空

`versioned_skiplist_lockfree.cc:143-154`

```cpp
if (succs[0] != tail_ && ... entity/column/target/entity_type 相同) {
  new_node->SetOlderVersion(succs[0]);
}
```

- 没有 `succs[0]->SetNewerVersion(new_node)`；`newer_version_` 构造后永远是 nullptr。
- 版本链建立条件包含 `entity_type`，但跳表排序**不包含** `entity_type`（见 1.3）：当同 `entity_id/column/target` 的 Vertex 与 Edge 相邻时，`succs[0]` 类型不同 → 不连 older，历史版本永久不可达（`GetAtTime`、`GetVersionChain` 都会丢历史）。

### 1.3 [P1][已确认] 跳表排序键与 CedarKey 契约不一致

排序条件（`versioned_skiplist_lockfree.cc:112-125`、`168-201`）：

```
entity_id ASC, column_id ASC, target_id ASC, timestamp DESC
```

而 `CedarKey::Compare`（`include/cedar/types/cedar_key.h:389-420`）是：

```
entity_id, entity_type, column_id, target_id, timestamp_be(~ts), sequence, flags
```

- **`entity_type` 不在跳表顺序里**，Vertex/EdgeOut/EdgeIn 会交错；`Insert` 的同版本判断又要求 `entity_type` 相同，导致链断（1.2）。
- **`sequence` 不在顺序里**：同一微秒的两次写（seq 不同）被放成"新在前"，与 `CedarKey` 的 seq 升序相反；flush 时 `FlushEntityGroup` 又按 `a.first < b.first` 重排（`lsm_engine.cc:1120-1123`），顺序才被纠正 —— 但这说明内存里的顺序和落盘顺序是两套规则，任何依赖"memtable 已有序"的逻辑都不可靠。
- 注释说"timestamp 降序与 FindLatestVersion 一致"，但降序依赖 `~ts` 编码的 `Compare` 才是全套契约。

**修法**：抽一个唯一的 `CedarKey::LogicalCompare`（先比 user key 再比 ts/seq/flags），跳表、flush、compaction、iterator 全部复用；`entity_type` 必须在 `column_id` 之前。

### 1.4 [P1][已确认] MVCC 版本号用的是"事务开始时间"，不是提交序号

`src/transaction/occ_transaction.cc:357-381`

```cpp
Timestamp txn_version = read_timestamp_;   // Begin() 时分配
...
write_set_.push_back({..., txn_version, ...});
```

- `Commit()` 里另分配 `commit_timestamp_`（`:156`），但**从不使用**；memtable 里存的是 begin 时间戳（`:614`）。
- 读路径 `entry.txn_version <= read_timestamp_`（`:258-269`）因此会看到"在本事务开始后才提交"的写：T2 在 T1 提交前 Begin（read_ts 更大），T1 提交后 T2 就能读到 T1 —— 违反快照隔离。
- 反过来，T1 的写版本号小于在它提交前 Begin 的 T3，T3 也能读到未提交（在 T3 读的时刻可能还没 WAL）的 T1。

**修法**：写集版本在 `Commit` 成功后用 `commit_timestamp_` 赋值；或维护 `commit_seq` 并在读侧比较 `commit_seq <= read_seq`。

### 1.5 [P1][已确认] 读取接口忽略 target_id / txn_version / tombstone

- `FindLatestVersion(entity,type,col)` 不比较 target（注释自己承认，`:223-224`），`GetLatest/GetAtTime` 走这条路径（`:269-330`）。
- `GetAtTime` 只沿 older 链回溯 `ts > query`（`:279-281`），不检查 `txn_version`，也没有 tombstone 判断。
- `LockFreeVSL::GetAtTime` 返回的 `Descriptor` 可能是 `Descriptor::Tombstone`，但调用方（`VSLMemTable::GetAtTime` → `LsmEngine::GetAtTime` → `OCCTransaction`）都没有过滤。
- `MarkDeleted()/IsMarked()` 是空实现（`:66-67`，直接 `return true/false`），说明墓碑语义从未落地。

### 1.6 [P1][已确认] 同一 key 重复插入不去重，version 链可含重复版本

`Insert` 不做"已存在则替换/跳过"，同 `(entity,col,target,ts,seq,flags)` 连续写会插入多个节点；`FindLatestVersion` 返回最先遇到的（新插入的），`GetVersionChain` 会返回重复版本；`FlushEntityGroup` 会把它们全部写进 SST（`lsm_engine.cc:1085-1092`），随后 `CompactionMerger::IsDuplicate` 只按 `entity/ts/target` 去重（忽略 sequence/flags），又可能删错。**修法**：写路径按完整 key 去重（或做 upsert）。

### 1.7 [P2][已确认] 内存回收缺失：hazard pointer 是死代码，节点只在析构时释放

- `include/cedar/storage/hazard_pointer.h` 存在，`src/storage/hazard_pointer.cc` 还被注释掉一段（`:79`），`LockFreeVSL` 完全没用。
- 节点在 `~LockFreeVSL` 才统一 delete（`:86-95`）；删除/覆盖的节点不可回收，长事务/大 memtable 下内存只增不减。
- 若 1.1 的并发插入造成"节点不在 level-0 链上"，析构时这些节点不会被 delete（泄漏）；反之若出现环，析构死循环。

### 1.8 [P2][已确认] RandomHeight 的随机源是自增计数器，首个节点固定 16 层

`versioned_skiplist_lockfree.cc:378-388`

```cpp
uint32_t rnd = rnd_.fetch_add(1, ...);
while (height < kMaxHeight && (rnd & 3) == 0) { height++; rnd >>= 2; }
```

- `rnd_` 初值 0 → 第一次 Insert 命中 height=16；之后是 16,1,1,1,2,1,1,1,3,... 的确定序列，不是随机分布；高度分布仍正确（1/4 概率升层）但首节点满高、与插入顺序强相关。
- 影响性能与最坏高度，不是正确性。

### 1.9 [P2][已确认] Traverse / flush / 读并发无保护；IsFull 单位错误

- `Traverse` 直接走 `head_->Next(0)`（`:359-370`），与并发 Insert/删除无同步。
- `VSLMemTable::IsFull`（`vsl_memtable.cc:92-95`）用 `ApproximateMemoryUsage() >= 64MB`，而后者是 `sizeof(LFNode) * 节点数` 的估算（`versioned_skiplist_lockfree.cc:372-376`），不包含 Descriptor 堆分配；且 `LsmEngine::Put` 根本不检查 `IsFull`（`lsm_engine.cc:150-162`），memtable 永不自动 flush。
- `size_` 在 `VSLMemTable::Put` 里再 +1（`vsl_memtable.cc:14`），而 `LockFreeVSL` 自己也维护 size，两个计数可能不一致。

### 1.10 [P2][已确认] 1000+ 行的 `delta_version_chain.h` 是死代码

`include/cedar/storage/delta_version_chain.h`（1134 行）没有任何 `#include`；`version_chain_index.h` 只被 `async_index_builder.h`/`mvcc_optimizations.h` 引用，而这两个也没有进入主写路径。仓库里同时存在 **4 套** 版本链实现（LockFreeVSL、CedarMemTable、delta_version_chain、version_chain_index），维护者无法判断哪套是权威。

## 2. 列式存储（Frond Zone-Columnar SST）

### 2.1 [P0][已确认] target zone 跨 block 拼接错位

- 每块编码时 `TargetIdZoneEncoder::Encode` 先写 1 字节编码类型（`zone_encoder.cc:577, 599`），再写位图/varint。
- `ZoneColumnarSstBuilder::FlushBlock` 把每块的 `encoded_data` 放进 `zone2_chunks_`（`zone_columnar_format.cc:739-742`），`Finish` 把这些块**首尾相接**写成一个 zone2（`:816-826`）。
- 读端只构造一次 `TargetIdZoneEncoder::Decoder(data, EncodingType::kRaw)`（`zone_columnar_format.cc:1152`），构造函数**只跳过第 1 个字节**（`zone_encoder.cc:615`），然后把剩余字节当连续 varint 解码。
- 结果：多 block 文件中，从第 2 块开始，每块的 1 字节类型前缀被当成一个 target 值 → **后续所有行的 target_id 错位**（边文件的 dst、Vertex 的 extension 全部错）。且若某块按 kDelta 编码（`same_as_entity > 80%` 时），解出来的是位图字节。

**修法（最小改动）**：target zone 固定用 kRaw 且去掉类型字节；或每块记录 `(offset,count,type)` 元数据，读端按块解码。**必须加多 block 回归测试**（>8192 行）。

### 2.2 [P1][已确认] flags bitmap 跨 block 错位，且只保留 tombstone 一位

- `EncodeFlagsBitmap` 每块生成 `ceil(n_block/8)` 字节（`zone_encoder.cc:767-778`），`Finish` 直接拼接（`zone_columnar_format.cc:837-845`）。
- 只有每块行数是 8 的倍数时，全局 `idx/8` 才对齐；否则第 2 块起所有 flag 错位。
- `EncodeFlagsBitmap` 只写 `kTombstone`；`DecodeFlagsBitmap` 也只恢复 `kTombstone`（`:810-826`），`kDeleted/kCompressed/kHasExtension` 全部丢失。
- `KeyMetadataZoneEncoder::Decoder::IsTombstone` 还直接按全局 bit 索引原始拼接串（`:869-872`）。

### 2.3 [P0][已确认] Entity Index 被禁用，且构建它仍然全量占内存

- 写端注释掉 `WriteEntityIndex()`（`zone_columnar_format.cc:872-876`），读端注释掉 `LoadEntityIndex()`（`:1112-1116`），但 `Add` 仍在为每行维护 `entity_index_builder_[entity_id].push_back(row)`（`:642-645`）——flush 期间 O(rows) 的额外内存与哈希开销，最后全部丢弃。
- `FindEntityPositionsFromIndex`（`:1231-1249`）在没有持久索引时返回空，但它的调用者（`Get`/`GetAtTime`）改用了 `entity_decoder_->FindEntityPositions`（内存线性扫描 + 100 次后建全量倒排），因此只是"慢"，暂未发现漏查。**注意**：一旦以后恢复持久索引路径，空 vector 会被当成"不存在"。

### 2.4 [P1][已确认] 点查忽略 target_id / column / seq，边会读错值

`ZoneColumnarSstReader::Get(key)`（`:1363-1387`）：

```cpp
auto positions = entity_decoder_->FindEntityPositions(key.entity_id());
for (size_t idx : positions) {
  uint64_t ts = timestamp_decoder_->Get(idx);
  if (ts == key.timestamp().value()) return value_decoder_->Get(idx);
}
```

只比较 entity + timestamp，不比较 `target_id/column_id/sequence/flags`。文件头虽然固定了 `column_id/entity_type`，但 **target_id 在文件内是变化的**（同一 src 的多条边、或有 extension 的 Vertex）。同 entity、同 ts、不同 dst 的两条边，点查会返回任意一条。`GetAtTime`（`:1389-1418`）同样只按 ts 找"最新"。

### 2.5 [P1][已确认] GetRange / ScanTemporalRange 把结果 key 重建成 Vertex

`zone_columnar_format.cc:1446, 1471, 1529`

```cpp
CedarKey key = CedarKey::Vertex(entity_id, column_id, Timestamp(ts));
```

- 对 edge 文件，返回的 key `target_id=0`、`entity_type=Vertex`。
- `LsmEngine::GetAll` 用它判断 `key.target_id()!=0 ? dst_id : nullopt`（`lsm_engine.cc:290-293`），于是 SST 里的边全部丢失 dst；去重逻辑（`:311-319`）也会把不同 dst 的边误判为重复。

**修法**：用 `header_.entity_type/column_id + target_decoder + metadata_decoder` 重建完整 key（与 `Iterator::Key()` 相同），`Iterator::Key()` 是正确写法（`:1585-1597`）。

### 2.6 [P1][已确认] 校验和从未计算、读取端从未校验；header 只校验 magic

- `WriteFooter`（`:988-1009`）只填 `entry_count/file_number/...`，`data_checksum/header_checksum` 保持 0；文件里也没有任何 CRC64 计算调用。
- `Open` 只检查文件大小和 offset 边界（`:1035-1120`），不校验 header.version（`DecodeFrom` 只验 magic，见 `:437-441`），不校验校验和。
- 解码器在越界/损坏时大量"静默返回 0/空"（`EntityIdZoneEncoder::Decoder::Get` `:180,186,195`；`ValueZoneEncoder::Decoder::Get` `:1047-1053`），损坏会被伪装成"空值/不存在"。

### 2.7 [P1][已确认] 每个 reader 把整个 SST 读进内存

`Open` 用 `new char[buffer_size_]` + 一次性读入（`:1048-1053`），`Close` 才释放。读路径（`LsmEngine::Get/GetAll/GetAtTime`）每次查询都可能 `ZoneColumnarSstReader reader(path); reader.Open()`（`lsm_engine.cc:234-243, 280-283`），意味着**每次点查复制整个文件**；`sst_reader_cache` 只在部分路径使用。大数据量下会 OOM/极慢。

### 2.8 [P2][已确认] Restart Points 记录的是文件第一个 key，且从未被使用

`FlushBlock`（`:716-720`）：

```cpp
ZoneRestartPoint rp;
rp.entity_id = first_key_.entity_id();          // 文件第一个 key，不是本块第一个
rp.timestamp_hi = first_key_.timestamp().value() >> 32;
rp.row_index = header_.row_count;
```

- `first_key_` 只在第一次 `Add` 时赋值（`:625-630`），所有块的 restart point 都指向同一个 entity。
- `BinarySearchRestartPoint` 只有声明没有实现；`Iterator::Seek` 是 O(n) 线性扫描且谓词是错的（`:1567-1577`：`entity>=` 且 `ts<=` 混比，忽略 type/column/target/seq），且全仓库没有调用者。即"稀疏索引"是写出来但完全没用的元数据。

### 2.9 [P2][已确认] Entity RLE 的 restart point 会漏掉跨 run 的索引

`EntityIdZoneEncoder::Decoder::BuildRestartPoints`（`zone_encoder.cc:143-164`）只在 `idx % 8192 == 0` 的记录边界记录 restart；如果一条 run 从 idx=8000 延伸到 8500，则 8192 没有记录。之后 `Get(8300)` 选择 restart_idx=1（对应 idx=8500），从 8500 开始扫描，永远找不到 8300，返回 0。**重复 entity（RLE 合并）跨检查点时读取错误**。当前 `Get` 主要被 iterator 使用；一旦恢复 iterator 的随机访问就会读到错行。

### 2.10 [P2][已确认] Bloom filter 实际是空的（从未分配位图）

`ZoneColumnarSstBuilder` 构造 `bloom_filter_(10)`（`zone_columnar_format.cc:607`）时 `num_keys=0`，`BloomFilter` 构造不会分配 `data_`（`bloom_filter.cc:21-34`）；`Add` 开头 `if (data_.empty()) return;`（`:44`）。因此 `EncodeTo` 写 0 字节、header `bloom_filter_size=0`、读端跳过，`MayContainEntity` 退化为只查 min/max（`:1538-1548`）。功能等于没有；如果以后有人把 `Add` 修好却忘了 `Finish` 前 resize，就会出现 false negative 漏查。

### 2.11 [P2][已确认] Zone Map 只覆盖最后一个 block

`WriteZoneMaps`（`:901-921`）遍历 `current_zones_`，而 `current_zones_` 在 `FlushBlock` 里每次被 `move`（`:756`），因此最终写出的 5 个 ZoneMapEntry 只统计最后一块；`Finish` 之前所有块的数据没有聚合。读端虽然解码到 `zone_maps_`，但没有任何查询使用它，所以目前只是"元数据撒谎"，一旦用于剪枝就会错。

### 2.12 [P2][已确认] 格式细节问题

- **header 写在文件末尾**（`:882-887`），footer 在它之前；`Open` 读最后 256B 当 header。格式上可行，但任何"在文件尾部 append"的操作都会破坏 header，且 `Footer` 的 `footer_offset` 必须精确，容错差。
- **每文件固定一个 `column_id + entity_type`**（header），flush 按 `(type,column)` 各建一文件（`lsm_engine.cc:1083-1101`）：列数 × 类型数 × flush 次数的文件数，元数据和文件句柄会爆炸。
- **字节序混用**：header/footer 用 fixed-endian；EntityId RLE 和 target/values 用 host-endian `memcpy`（`zone_encoder.cc:115, 944, 980`），不可跨平台。
- **zone1 时间戳是全局 delta-of-delta**，必须全解才能随机访问（`Decoder` 构造即全解，`:383-439`），文件大时内存/CPU 高；且 delta 计算用 `int64` 强转 uint64，时间戳 > INT64_MAX 时未定义行为（实际微秒时间戳不会）。
- **`ValueZoneEncoder` 的字典编码被强制回退成 kRaw**（`zone_encoder.cc:1124-1136`），注释明说"format 不支持"；列存最大的压缩收益（低基数属性）没有兑现。

## 3. Compaction 与 LSM 集成

### 3.1 [P0][已确认] 合并只处理 input_files，却删除 overlapping_files → 直接丢数据

`size_tiered_compaction.cc:654-756`

```cpp

  RemoveFileFromLevel(f.file_number, task.output_level);   // 下层文件直接删掉
```

### 3.2 [P0][已确认] Flush 丢弃 tombstone；compaction 的 tombstone 逻辑是双死的

- `FlushMemTable`：`if (!descriptor.IsTombstone()) { ... }`（`lsm_engine.cc:1086`）——删除标记不落盘。
- `Delete` 写的是 `Descriptor::Tombstone`（`occ_transaction.cc:383-389`），不是 key 的 `flags`；而 `CanDropTombstone` 判断的是 `key.flags() & 0x08`（`compaction_merger.cc:61`），永远为假。
- `ShouldDropTombstone`（`size_tiered_compaction.cc:875-893`）从未被调用（`MergeZones` 里只有 TODO，`:837-838`）。
- 所以：**flush 后删除失效（数据复活），compaction 也永远不会清墓碑**。
- ✅ **已修复（T2 / 计划 Task 1.1）**：flush 不再跳过墓碑；Get/GetAtTime/GetAll/GetRange/GetRangeLimit 统一过滤墓碑（同 (timestamp, dst_id) 版本槽位上墓碑优先）；LsmEngine::Delete 用 Descriptor::Tombstone(key.column_id()) 保证墓碑归属正确的列分组；compaction 侧保持不清理墓碑（Phase 4 之前 ShouldDropTombstone 保持 false）。测试：FlushRecoveryTest.DeleteSurvivesFlushAndReopen、FlushRecoveryTest.TombstoneHiddenFromAllReadPaths（tests/storage/test_flush_recovery.cc）。

### 3.3 [P0][已确认] 没有 WAL 重放；直接 Put 路径根本不写 WAL

- `WalReader` 已实现（`wal.cc:486+`），但 `grep -rn Replay|Recover` 只找到 `Database::Recover`（`database.cc:442`），它只打开 storage，没有任何 WAL 读取/重放；"fast recovery 跳过 WAL replay" 的注释与代码不符。
- `CedarGraphStorage::Put` 等直接路径只调 `engine->Put`（`cedar_graph_storage.cc:149-155`），`LsmEngine::Put` 只写 memtable（`lsm_engine.cc:150-162`），不写 WAL；只有 `OCCTransaction::Commit` 写 WAL（`occ_transaction.cc:179-188`），而它同样无人重放。
- 结论：**崩溃后自上次 flush 之后的所有写入（无论是否事务）都不可恢复**；而 flush 没有自动触发（见 3.4），这个窗口可能是整个进程生命周期。
- ✅ **已修复事务路径（T2 / 计划 Task 1.2）**：OCCTransaction::Commit 改为 WAL-first（写集 + 提交围栏落同一条 WAL record → 成功后才写 memtable），Put 同步填充 wal_batch_ 且与 memtable 使用同一个 CedarKey；新增 src/storage/wal_replay.cc（WalReplay::Replay）在 LsmEngine::Open 的 LoadSstFiles 之后、接受写之前重放，未提交事务不落表、按 (key, txn_version, descriptor) 去重幂等，截断/CRC 错的崩溃尾巴被容忍；LsmEngine::InitWAL 关闭 WalWriter 的异步组提交（group_commit_timeout_us=0）并新增 WriteWALBatch 串行 append+sync，使 Commit 能拿到真实 WAL 结果。
  ⚠️ 直接 LsmEngine::Put/Delete 路径仍不写 WAL（本次未扩大范围）：混用事务写与直接写时，旧 WAL record 可能在重放时覆盖更新的墓碑；根治需要 WAL checkpoint/truncation（按 flush 水位截断），列为后续任务。测试：FlushRecoveryTest.WalReplayRecoversCommittedTransactionAfterCrash（子进程 SIGKILL 后重开）、.WalReplaySkipsUncommittedTransaction、.WalReplayIsIdempotentAcrossReopen、.WalFailureKeepsDataInvisible（Env 注入 Append 失败）、.WalFileListingIsNumericallyOrdered、.TruncatedWalTailDoesNotBreakOpen。

### 3.4 [P1][已确认] 没有自动 flush 触发；`ForceFlush` 失败会直接丢数据

- `LsmEngine::Put` 不检查 `mem_->IsFull()`，`AutoCompactionThread` 只检查 compaction（`lsm_engine.cc:AutoCompactionThread`），没有"memtable 满 → flush"的路径；只有显式 `ForceFlush()`。
- `ForceFlush`（`:932-955`）把 `mem_` move 到 `imm_`、新建 memtable、解锁、flush；**无论 `FlushMemTable` 成功与否，都 `imm_.reset()`**（`:951-952`）——IO 失败时这批数据静默消失。
- `ForceFlush` 期间 `imm_` 非空时并发调用返回 `IOError("flush already in progress")`（`:935-937`）；如果调用方是 `options.sync=true` 的写，写会报错，但对调用方语义不明确。
- ✅ **已修复（T2 / 计划 Task 1.3）**：Put 之后按 ApproximateMemoryUsage() >= write_buffer_size 自动换表并 flush（同步执行，后台化留给 Phase 4）；ForceFlush 失败时保留 imm_，重试可成功；Close 传播 flush/WAL 错误。测试：FlushRecoveryTest.AutoSwitchTriggeredByMemoryUsage、.ForceFlushFailureKeepsDataAndRetrySucceeds（只读目录注入 IO 失败）。

### 3.5 [P0][已确认] 活跃事务持有旧 memtable 裸指针，flush 后悬空

- `BeginTransaction` 把 `mem_.get()` 存进 `OCCTransaction::memtable_`（`lsm_engine.cc:1037-1043`）。
- `ForceFlush` 替换 `mem_` 并最终 `imm_.reset()`（`:943-952`）销毁旧表；此时仍活跃的事务在 `Commit` 的 `WriteToMemTable()` 里写这个已释放对象 → **use-after-free**。
- 同时，即使没 UAF，事务写入的旧表正在被 flush，flush 的 `Traverse` 与事务的 `Insert` 并发，数据竞态。

**修法**：memtable 生命周期用 `shared_ptr` + flush 前等待引用归零；或事务在 Commit 时重新获取当前 memtable 并做写冲突检查。
- ✅ **已修复（T2 / 计划 Task 1.3）**：mem_/imm_ 改为 std::shared_ptr<VSLMemTable>；读路径（Get/GetAll/GetAtTime/GetRange/GetRangeLimit/GetStats/GetTemporalChain）先持强引用再访问，写路径在共享锁内完成（换表拿独占锁，写到一半不会被换走）；事务不再解引用 Begin 时捕获的裸指针——OCCTransaction 的读写统一走新增的 LsmEngine::PutPinned/LsmEngine::GetVersionChain，写总是落到当前 memtable。验证：FlushRecoveryTest.ConcurrentPutAndFlushKeepsAllRows（4 写 + 2 读 + 1 flush 线程）在 TSan 构建下 5/5 无报告（TSan 不支持多线程 fork 后建线程，两个崩溃恢复用例在普通构建下验证）。

### 3.6 [P1][已确认] Compaction 调度会重复执行同一任务；文件并发合并无主

- `ScheduleCompaction` 每次都 `PickNextCompaction()` 再 push（`:565-573`），**不检查队列里是否已有同 level 任务**；`AddSSTFile`（`:374-378`）、后台线程（`:644`）都会触发。
- `PickNextCompaction` 在 `levels_mutex_` 下检查 `compacting_files_`（`:462-474`），但 `ExecuteCompaction` 才在**任务被弹出后**把文件标记为 compacting（`:530-539`）。多个 compaction 线程（`config_.compaction_threads`）可以同时 pick 到同一批文件 → 两个任务同时读写同一输入，后完成者删除先完成者的输入文件。
- `LsmEngine::AutoCompactionThread` 自己也在 `PickNextCompaction + ExecuteCompaction`（`lsm_engine.cc`），与 `SizeTieredCompactionEngine` 自己的 N 个后台线程**并行**，竞争进一步放大。

### 3.7 [P1][已确认] `RemoveFileFromLevel` 无锁修改 `levels_` 并删除物理文件

`size_tiered_compaction.cc:998-1019`

- 调用点在 `DoZoneCompaction` 的锁外（`:743-750`），而 `GetFilesForEntity/GetLevelFiles/AddSSTFile` 都在锁内读写同一个 vector → **数据竞态 / vector 迭代器失效 / UB**。
- 函数内 `std::filesystem::remove(it->path)` 立即删 SST；并发读路径可能刚拿到 meta 并准备 `reader.Open(path)` → 读到不存在/半删除文件。
- 没有"文件引用计数 / 读快照"机制（`GetFilesForEntity` 只返回拷贝的 meta）。

### 3.8 [P1][已确认] Blob 引用在 compaction 中只拷贝指针，旧 blob 删了也不管

`HandleBlobReference`（`:895-910`）注释"仅拷贝指针（延迟拷贝策略）"，然后原样返回 `Descriptor`。

- compaction 输出 SST 的 meta 不登记 `blob_file_number`（`DoZoneCompaction` 的 `output_meta` 没赋值，`:702-734`），新 SST 对旧 blob 没有引用计数。
- `RemoveFileFromLevel` 对被删输入 SST 调 `RemoveReference`（`:1007-1009`），引用计数归零后 `TriggerBlobGC` 会删 blob 文件（`:969-985`）——新 SST 里的 BlobRef 变成悬空指针，读取时 `GetValue` 失败或读出错误数据。
- flush 路径同样不登记 blob：`FlushEntityGroup` 只设置 `zone_meta.blob_path`，`blob_file_number/blob_file_size` 为 0（`lsm_engine.cc:1191-1192`）。

### 3.9 [P1][已确认] 两套 levels 元数据不同步

- `LsmEngine` 自己维护 `levels_` + `column_file_index_`（`lsm_engine.cc:481-484`），compaction 引擎维护另一套 `levels_`（`size_tiered_compaction.cc:277`）。
- Flush 往两边都加（`lsm_engine.cc:1173, 1194`）；**compaction 只更新压缩引擎那套**（`size_tiered_compaction.cc:739-750`），`LsmEngine::levels_` 永远停留在 flush 时的状态。
- `LsmEngine::GetEntriesFromSst`（`:1377-1417`）与 `column_file_index_` 仍用旧 meta：可能指向已删除文件；`DoCompaction`（`:1205-1319`）也读这套旧 meta，且**全仓库没有调用者**（死代码）。
- `column_file_index_` 存的是 `&levels_[level].back()` 的裸指针（`:1176`），后续 `push_back/erase` 使 vector 扩容或移动 → 悬空指针；回退路径还 `const_cast` 指向 `levels_` 元素的指针并在锁外使用（`:1389-1399`）。

### 3.10 [P1][已确认] `LsmEngine::DoCompaction` 是死代码且逻辑错误；调用 `RemoveSSTFile(输出文件号)`

`lsm_engine.cc:1205-1319`

- 若被启用：`DoCompaction` 只合并同 `(entity_type,column)` 的输入（`:1214-1220`），但 `SelectCompactionFiles` 按 file_number 取 4 个文件（`:1340-1342`），可能跨列 → 直接 `InvalidArgument`，压缩循环可能卡死。
- 末尾 `compaction_engine_->RemoveSSTFile(output_meta->file_number)`（`:1314`）意图删输入却传了输出号：输出文件尚未 `AddSSTFile`，返回 NotFound，**输入文件在压缩引擎里仍然登记**，后续会再次被选中、读到已删除路径。

### 3.11 [P2][已确认] `CompactionMerger` 的去重键不完整；`output_level_` 永远 0

`compaction_merger.cc`

- `IsDuplicate` 只比 `entity_id/timestamp/target_id`（`:44-51`），忽略 `sequence/flags`；同 ts 不同 seq 的版本会被当重复丢掉一个。
- 堆比较 `MergeHeapItem::operator>` 用 `key > other.key`（`compaction_merger.h:25-27`），完全相等的 key 之间没有稳定次序，保留哪份 value 取决于堆实现。
- `CanDropTombstone` 依赖 `output_level_`（`compaction_merger.h:68`），但没有任何 setter，且 `LsmEngine::DoCompaction` 不设置 → 永远 0 → 永远不丢 tombstone（而 tombstone 反正也没写进 key.flags）。
- `Run` 里 `stats_.input_entries` 只统计每个迭代器的第一条（`:33-40`），压缩率统计无意义。
- 输出 `builder` 用默认 `CedarOptions options;`（`:79`），不继承 DB 的 block size/compression/blob 配置；`meta` 不填 min/max，调用方用默认 0 初始化后取 min → `min_timestamp=0`（`lsm_engine.cc:1256-1263` 只对 entity 初始化了输入[0]，timestamp 没有），时间范围剪枝退化。

### 3.12 [P2][已确认] 崩溃安全：输出直接写最终路径，MANIFEST 无 fsync/原子安装

- `DoZoneCompaction` 直接 `NewWritableFile(output_path)`（`:656-662`），没有 `.tmp` + rename；中途崩溃留下半截 SST，而 `levels_` 尚未登记它（不容易被读到），但文件会泄漏。

### 3.13 [P2][已确认] 资源与调度缺陷

## 4. 设计不完善清单（能力缺失 / 死代码 / 测试）

### 4.1 缺失能力

1. **无 WAL 重放**（见 3.3）——这是存储引擎最基础的恢复路径。
2. **无合并/版本保留策略**：`MergeZones` 不做同 key 去重（注释说"跳过"，代码没写，`:833-835`），保留全部版本；没有"保留最近 N 版 / 按快照水位 GC"的机制，且没有任何读快照登记（`compaction_merger.cc:59-60` TODO）。
3. **无墓碑协议**：`Descriptor::Tombstone`、`key.flags::kTombstone`、`ShouldDropTombstone` 三套语义互不相通（见 3.2）。
4. **无 memtable 自动切换/写停顿/背压**：`IsFull` 无调用者，写入无速率限制，`ForceFlush` 并发直接报错。
5. **无读快照/文件引用计数**：compaction 删除文件、blob GC 都不检查活跃 reader（见 3.7/3.8）。
6. **无持久化 Entity Index / Bloom / Restart Point 的读取路径**：三者都是"写了但不用"。
7. **无损坏检测**：CRC 字段形同虚设（2.6）。

## 6. 建议的最小验证实验（写测试即可复现）

1. **多 block target 错位**：构造 1 个 edge 列、9000 行、dst 各不相同的 memtable → flush → `GetAll`/`Iterator` 读回，比对前 8192 行与之后的 dst。预期第 8193 行起错位（2.1）。
2. **tombstone 复活**：Put(k1) → flush → Delete(k1) → flush → `Get` 仍返回旧值（3.2）。
3. **compaction 丢下层**：L0 放 4 个文件触发 compact 到 L1；再让新 L0 与 L1 范围重叠并 compact；检查被删的 overlapping 文件里的 entity 是否还能查到（3.1）。
4. **并发写**：8 线程各写 10k 个不同 entity 到同一 memtable，flush 后统计行数；预期少于 80k 或崩溃（1.1）。
5. **崩溃恢复**：写 1000 条（不 flush）→ 杀进程 → 重新 open → 统计可见条数；预期 0（3.3）。
6. **快照隔离**：T1 Begin(w1) → T2 Begin 读 → T1 Commit → T2 再读；预期 T2 不应看到 T1（1.4）。
7. **序列化 round-trip**：`ZoneColumnarSstBuilder` 写 N=1, 8191, 8192, 8193, 20000 行（含 tombstone flag、seq 非 0、边）→ `ZoneColumnarSstReader` 逐行比对 key+value（2.1/2.2/2.5）。

## 8. 交叉复核补充（VSL / 事务 / 边 API）

以下条目由同工作树的独立子审计提出，我已逐条对照源码复核，确认成立；编号接续正文。

### 8.1 [P0] 批量写边丢 dst，且 WAL 与 memtable 的 key 不一致

- `WriteBatch::ToWriteSet` 构造 `CedarKey` 时把 `dst_id` 放进了 key（`batch_api.cc:322-323`），但 `WriteSetEntry` 构造只传 7 个参数，`target_id` 取默认 0（`batch_api.cc:326-327` 对照 `occ_transaction.h:119-126`）。
- `WriteToMemTable` 又用 `entry.target_id` 重建 key（`occ_transaction.cc:609-614, 638-654`），于是 memtable 里的边 dst=0；而 WAL 批次用的是 `entry.key`（`occ_transaction.cc:419`），带正确 dst → **WAL 与内存/落盘不一致**，恢复后同一条边变成两种 key。
- 影响：批量导入的边全部写成 dst=0；同 src/type 的不同 dst 还会被 `PutBatch` 覆盖（去重只看 entity/type/column，`occ:400-410`）。
- 修法：`ToWriteSet` 传 target_id；WAL 与 memtable 统一使用 `entry.key`，不要重建；`PutBatch` 去重键加入 target_id。

### 8.2 [P1] 边读取 API 丢 dst / 参数错位

- `CedarGraphStorage::GetEdge` 构造了带 dst 的 `edge_key` 却没用，实际调用 `GetAtTime(src, EdgeOut, edge_type, ts)`（`cedar_graph_storage.cc:253-256`），而 `LsmEngine/VSLMemTable::GetAtTime` 没有 target 参数 → 返回任意 dst 的边。
- `ScanEdges` 明确"暂时返回 src_id 作为占位"（`:275-279`）。
- `GetDynamicEdge` 把 `property_id` 当 `edge_type` 传给 `GetAtTime`（`:741`），参数错位。
- 修法：`GetAtTime/GetLatest/GetVersionChain` 全链路加 target_id（或在 key 里比较 target），补 `GetEdge(dst)` 的精确查询。

### 8.3 [P1] txn_version 的"域"被到处混用

- `PutStaticVertex` 用 `Timestamp::Now()` 当 txn_version（`cedar_graph_storage.cc:590`），直调 Put 路径用 `key.timestamp()`（`graph_db_impl.cc` 约 201 行），OCC 用 begin ts（`occ:375`），读侧统一按 `<= read_timestamp_` 比较 → 三种时钟混在一起，MVCC 判断不成立。
- 非事务读（`LsmEngine::Get/GetAtTime/GetAll`）完全不看 txn_version（`lsm_engine.cc:191-211, 324-344`）。

### 8.4 [P1] OCC 验证仍可能 lost update

- 写-写验证只取 `chain_opt.front()`（`occ:490-513`），不看 target、不看 sequence、不遍历整条链；且比较方向是 `latest.txn_version > read_timestamp_`——版本号是 begin ts，一个"先 Begin、后提交"的并发事务版本号更小，直接漏检。

### 8.5 [P1] 其他确认项

- `GetAllColumns` 的 `column_ids` 恒为空（`occ:307-312`），函数永远返回空列集。
- `GetTemporalChain` 只查 `mem_`（`lsm:901-918`），不查 SST，时间旅行链在 flush 后丢失。
- `Abort/Cleanup` 不清 memtable（`occ:198-219, 630-636`）；结合 3.3 的"先 memtable 后 WAL"，WAL 失败后已写 memtable 的数据继续可见。
- `PutStaticVertex/PutStaticEdge` 用 `Timestamp::Now()` 作为 txn_version，与业务有效时间 `Timestamp::Static()`（=1）不是一回事，静态属性的快照可见性不可控。

### 8.6 死代码与构建配置补充

- `version_chain_index.h` 的 `FindAtTimeUnlocked` 对 sentinel 空指针解引用（`:542-545, 599`），但 `AsyncIndexBuilder` 从未实例化，属潜伏 bug。
- `hazard_pointer.cc`、`mvcc_optimizations.h`、`vsl_adapter.h` 均未进 CMake；`vsl_adapter.h` 还 include 了不存在的头；`optimized_skiplist.h` 只有声明无实现。
- `cedar_memtable.cc` 编译但无实例；其 `InternalKey` 丢 target、`NewIterator` 未定义、第 344 行还留 debug `cerr`。
- `CMakeLists.txt` 仍是 `CXX_STANDARD 17`（`CMakeLists.txt:4`），与主分支 README 要求的 C++20 不一致；0.1 目前能编过只是因为用到的特性还在 C++17 内。

> 注：8.1/8.2 与 1.5、2.4、2.5 是同一个根因——"target_id 没有贯穿 key→memtable→SST→查询 API"，修复时应作为一个原子改动，而不是逐点打补丁。

## 9. 交叉复核补充（Compaction / LSM 集成）

以下条目来自对同一工作树的独立 compaction 审计，我已对照源码复核关键结论。**先给可达性结论**，它改变了正文 3.x 的定性：

| 实现 | 可达性 |
|---|---|
| `size_tiered_compaction.cc` | **活路径**：`FlushEntityGroup → AddSSTFile`、`LsmEngine::AutoCompactionThread`、engine 自己的后台线程 |
| `compaction_merger.cc` | **死代码**：唯一调用者 `LsmEngine::DoCompaction` 无调用者 |
| `block_level_compaction.cc` | 死代码：全仓库无引用 |
| `parallel_compaction_engine.cc` | 死代码：无引用，且大量方法只有声明 |
| `streaming_compaction_merger.cc` | 未编译，且类声明与 `parallel_compaction_engine.h` 不一致 |

因此正文 3.11（`CompactionMerger`）是"如果启用会怎样"的分析；**真正会改数据的是 `SizeTieredCompactionEngine::MergeZones/DoZoneCompaction` 和 `LsmEngine::FlushMemTable`**。

### 9.1 [P0] 压缩把不同 (entity_type, column_id) 的文件混在一起

- `PickNextCompaction` 直接取**整层** `levels_[level].files`（`size_tiered_compaction.cc:479`）；而 flush 是按 `(entity_type, column_id)` 各建文件（`lsm_engine.cc:1083-1101`），同一层里天然有多列/多类型。
- `DoZoneCompaction` 只用 `input_files[0]` 的列/类型建 builder 和输出 meta（`size_tiered_compaction.cc:674-677, 711-713`），`MergeZones` 把所有文件的 key 写进同一个 builder。
- 输出文件只有一个 header（单 `column_id + entity_type`）；读端 `ZoneColumnarIterator::Key()` 又用该 header 重建**每一行**（`zone_columnar_format.cc:1595-1596`）→ 其他列/类型的行全部被改写成首文件的列/类型；`GetFilesForEntity` 再按输出 meta 的 column 过滤（`size_tiered_compaction.cc:927`）→ 这些数据**查不到**。
- 结论：**第一次 L0 压缩（>阈值）就会把其他列/类型的数据改写或隐藏**。修法：compaction 任务必须按 `(entity_type, column_id)` 分组，`PickNextCompaction` 只选同组文件。

### 9.2 [P0] 两套文件号分配器会撞号，flush 覆盖压缩输出

- flush 用 `LsmEngine::next_file_number_`（初始 1，`lsm_engine.cc:28`，`:1112`）；压缩输出用 `SizeTieredCompactionEngine::next_file_number_`（初始 1，`size_tiered_compaction.h:419`，`:656`）。
- 每次 flush 后两者恰好都等于"最大文件号 + 1"（`AddSSTFile` 会把压缩引擎计数器推到 `meta.file_number+1`，`size_tiered_compaction.cc:362-363`）。一次压缩输出 `N+1` 后，**下一次 flush 仍从 LsmEngine 的 `N+1` 取号** → 写同一个 `<N+1>.frond`，覆盖刚压缩出的文件；`SstReaderCache` 还可能继续返回旧内容的 reader。
- 修法：单一 allocator（或每次压缩后把新号回写 LsmEngine/manifest），并回填 `next_file_number_` 的持久化。

### 9.3 [P0/P1] 重启时同一文件被重复登记到 L0 和 L1

- `LoadSstFiles` 扫描目录，把**所有** `.frond` 一律设为 `meta.level = 0`（`lsm_engine.cc:1487`）。
- `Open` 先 `compaction_engine_->Open()` 从 MANIFEST 恢复高层文件（`:89-97`），随后 `MigrateExistingSstFiles()` 又把 `levels_`（全是 L0）里的文件按 `level=0` 加入压缩引擎（`:103-104`，`MigrateExistingSstFiles` 内 `zone_meta.level = level`）。
- `AddSSTFile` 只**同级**查重（`size_tiered_compaction.cc:352-357`）→ 同一 file_number 同时出现在 L0 与 L1。之后 L0 压缩会物理删除该文件，L1 元数据悬空；L1 压缩持续失败。注释"静默添加，不触发 Compaction"也是错的：`AddSSTFile` 在 L0 会 `ScheduleCompaction`（`:373-377`）。

### 9.4 [P1] Checkpoint 使用过期的 `LsmEngine::levels_`

压缩只更新 `SizeTieredCompactionEngine::levels_`（`size_tiered_compaction.cc:737-750`）；`LsmEngine::levels_` 只在 flush 时追加、从不删除（`lsm_engine.cc:1179-1200`）。`CreateCheckpoint` 走 `GetSstFiles`（`graph_db_impl.cc:452-478`）→ 检查点漏掉压缩输出、却包含已删除的输入，备份不完整。

### 9.5 [P1] 读与 compaction 删除文件竞态

`Get/GetAll/GetAtTime` 先拿文件元数据快照（`lsm_engine.cc:216-244, 270-296, 348-380`），compaction 之后 `RemoveFileFromLevel` 直接 `filesystem::remove`（`size_tiered_compaction.cc:998-1018`）；reader `Open` 失败被 `continue` 静默当"无数据"。没有文件 pin/延迟删除/epoch。与 3.7 是同一根因。

### 9.6 [P1] MANIFEST 保存/加载的并发与崩溃一致性

- `SaveManifest` 先 open tmp 再加锁（`size_tiered_compaction.cc:1025-1030`），并发调用可能互相截断/rename 失败；写错误不检查就 rename；无 fsync。
- `DoZoneCompaction` **先删物理输入，后 SaveManifest**（`:736-755`）：中途崩溃 → MANIFEST 仍指向已删除文件。
- `LoadManifest` 短读时 `next_file/num_levels` 可能未初始化即使用（`:1091-1100`），`path_len` 无上界（`:1126-1129`）。

### 9.7 [P2] 未接线的引擎与统计

- `block_level_compaction.cc`：inputs 为空时访问 `inputs[0]`（`:56-59`）UB；`ExecuteTask` 空实现；`CalculateWriteAmplification` 重复计数；`BlockIndex` 直接 memcpy 结构体、无校验/字节序。
- `parallel_compaction_engine.cc`：`ScheduleIfNeeded` 只算优先级后 `return true` 从不入队；`PendingTasks` 恒 0；`Submit/Schedule/PopForColumn` 等只有声明。
- `streaming_compaction_merger.cc`：未编译、类声明不一致、tombstone 仍按 `key.flags` 且 L3+ 直接丢。
- 统计：`CompactionMerger` 的 builder 不设 file_number/level → footer 为 0；`SizeTiered` 的 `total_input_bytes/output_bytes` 从不累加（`:225-233`）。

### 9.8 关键停止措施（先于任何"打开 compaction"的动作）

1. 在 9.1/9.2/9.3 修复前，**不要启动任何 compaction**。
2. 只设 `enable_background_compaction=false` **无效**：`LsmEngine::Open` 无条件 `auto_compaction_enabled_.store(true)` 并启动 `AutoCompactionThread`（`lsm_engine.cc:99-101`），该线程直接 `PickNextCompaction + ExecuteCompaction`，不看配置。
3. 与 compaction 无关但同样要先修的：flush tombstone（3.2）、memtable 生命周期（3.5）、WAL 重放（3.3）。

## 10. 交叉复核补充（Frond Zone-Columnar）

第三轮独立子审计聚焦列式格式，以下条目我已复核关键代码。

### 10.1 [P0] 单行 SST 的时间戳解码为空 → 整个文件读不出来

- 编码器对 n=1 只写 8 字节首时间戳（`zone_encoder.cc:353-361`）。
- 解码器把 `decoded_cache_.push_back(first_ts_)` **放在 `if (data_.size() > 8)` 分支内**（`zone_encoder.cc:390-407`）；n=1 时 `data_.size()==8`，缓存保持为空，`total_count_=1`。
- 后果：`TimestampDecoder::Get(idx)` 返回 0（`:445-448`），`FindTimeRange` 返回空（`:521-540`）。于是：
  - `Get(key)` 用 `ts == key.timestamp()` 比较（`zone_columnar_format.cc:1379-1383`）→ 永远不相等，点查 miss；
  - `GetAtTime` 的 `ts <= query && ts > best_ts` 因 ts=0、best_ts=0 恒假 → 返回 nullopt；
  - `Iterator::Key()` 把该行时间戳重建成 0，compaction 会把数据改写成 ts=0。
- **触发面非常大**：flush 按 `(entity_type, column_id)` 分组，单独一次属性写入就会生成一个只有 1 行的 SST；这类文件全部不可读。
- 修法：解码器在 `data_.size() == 8` 时也要 `decoded_cache_.push_back(first_ts_)`；补 n=1/2 的 round-trip 测试。

### 10.2 [P1] Blob 读取把 payload 前 4 字节当长度（二次剥离）

`BlobFileReader::Read` 已经 pread 了 4B 长度头、并从 `offset+4` 读数据（`blob_file.cc:314-333`）；但 `SimpleSSTBlobManager::ReadBlob` 又对返回 buffer 的前 4 字节做 `reinterpret_cast<uint32_t*>` 当 `actual_size`（`zone_columnar_format.cc:81-92`），随后 `assign(buffer+4, actual_size)`。任何 Blob 读取都会得到错误长度（可能越界抛异常）。当前 `AddValue` 在 src 内没有调用方，属"启用即 P0"。

### 10.3 [P1] AddValue 把 5~6 字节值静默写成 Tombstone

`AddValue` 对 `size()<=6` 的值走 `Descriptor::InlineShortStr`（`zone_columnar_format.cc:662-670`），而 `InlineShortStr` 上限是 4 字节（`descriptor.h:31`）→ `nullopt` → `desc = Descriptor()`（Tombstone）。5~6 字节值静默变成删除标记。

### 10.4 [P1] LSM 查询只查前 10 个文件，且用第一个 entity 推文件列表

- `GetRangeLimit/BatchGetRangeOptimized` 等处限制 `kMaxFilesToQuery = 10`（`lsm_engine.cc:559`、`:723`），超出直接 break → 静默漏结果。
- `GetBatchRange` 用 `entity_ids[0]` 调 `GetFilesForEntity` 代表所有 entity（`:707-710`），注释自己写"假设所有 entity 分布相同"。

### 10.5 [P1] 损坏文件边界：Open 不校验 zone_maps/restart_points，32 位偏移可回绕

`Open` 只在 `offset > 0 && size > 0` 时直接 `buffer_data_ + offset` 解码 zone maps/restart points（`zone_columnar_format.cc:1077-1095`），没有 `offset+size <= buffer_size_` 检查；且 offset/size 都是 `uint32`，加法可回绕。配合"校验和从不校验"（2.6），一个损坏/恶意文件可触发 OOB 读。

### 10.6 [P1] 对 optional decoder 直接解引用

`GetRange/ScanTemporalRange/GetAtTime/BatchGetRange` 直接 `timestamp_decoder_->...`、`entity_decoder_->...`（`zone_columnar_format.cc:1379, 1403, 1438, 1521`），不检查 `has_value()`；缺 zone 的文件（如空文件/截断文件）会 UB。`GetValue` 对 `value_decoder_` 有检查，其他路径没有。

### 10.7 [P1] FindTimeRange 在 start > end 时 size_t 下溢

`positions.reserve(ub - lb)`（`zone_encoder.cc:532`）：当 `start_ts > end_ts` 时 `lb > ub`，无符号相减回绕成巨大值 → `reserve` 抛 `length_error`/OOM。调用方没有 start<=end 校验。

### 10.8 [P1] Reader/缓存的生命周期与线程安全

- `ZoneColumnarSstReader` 的惰性索引（`EntityIdZoneEncoder::Decoder::BuildEntityIndex`、`TimestampZoneEncoder::Decoder::BuildSortedIndex`）在 `const Get` 中修改 `mutable` 成员（`zone_encoder.cc:251-278, 457-474`），而 `SstReaderCache` 会把同一个 reader 交给并发查询（`lsm_engine.cc:842-871`）→ 数据竞争（重复构建/读到半构建索引）。
- `SstReaderCache` 淘汰逻辑在"容量满且所有 reader 都被 pin 住"时只把队首移到队尾，`while` 不退出（`src/storage/sst_reader_cache.cc` 附近，子审计指出 31-34/70-90，需运行确认死循环条件）。
- 损坏/被删文件在 `Get/GetAll/GetAtTime` 中 `Open` 失败一律 `continue`（`lsm_engine.cc:236-243, 281-283, 368-371`），查询静默返回部分结果。

### 10.9 [P2] 其余格式问题（与正文 2.x 合并看）

- `header.zone*.data_offset`、`row_count`、`restart_points_count` 都是 `uint32`：文件 >4GB 或 >40 亿行回绕（2.12）。
- `GetValue` 对内联 int/float 直接 `AsInlineShortStr()` 返回空串（`zone_columnar_format.cc:1274-1277`），只有 Blob/短字符串能读。
- `GetAtTime` 的 `best_ts=0` 使时间戳为 0 的合法版本永远选不中（`:1407-1414`）。
- `TimestampZoneEncoder` 的种子 delta 用 `int64` 强转 uint64（`:364, 370`），时间戳 > INT64_MAX 时实现定义；当前微秒时间戳不会触发，但格式未声明该约束。
- `GetRangeLimit` 的 `limit` 在 SST 侧不生效（先取全部再截断），且返回顺序与"最新优先"未定义。
- `ColumnarReader`（`zone_encoder.cc`）与 `ZoneColumnarSstReader` 两套 reader 重复；`column_coders.cc` 是第三套编码实现（含首值丢失、65535 零游程冲突等 bug），均未在主路径使用。

> 注：10.1 与 3.2、3.5 一起构成"写入路径看似成功、重启/落盘后数据消失"的三个独立原因，建议同一批修复并在第 6 节补 n=1 的 round-trip 测试。



### 10.10 列式审计完整版的补充细节（均已对照源码确认）

- **Blob 尺寸/耐久性**：`Descriptor` 的 `size_kb` 是 `uint16`（`zone_columnar_format.cc:66-79`），对齐后大小达到 64MB 时除 1024 得到 65536 → 截断为 0；`aligned_offset` 又用 `uint32`（`blob_file.cc:187+`），blob 文件 >4GB 回绕。`Finish` 里 SST 先 `Sync`，Blob 后 `Close` 却不 fsync（`zone_columnar_format.cc:889-895`），崩溃后可能出现"SST 已持久、引用的 Blob 未持久"。
- **Target 解码 O(n²)**：`TargetIdZoneEncoder::Decoder::Get` 每次从头部线性扫描（`zone_encoder.cc:631-643`），而 `Iterator::Key()` 每行都调用它（`zone_columnar_format.cc:1585-1601`）→ `GetAllEntries`/compaction 遍历大文件是 O(n²)，8192 行以上就会明显变慢。
- **GetRangeLimit 可能返回最旧版本**：`FindTimeRange` 把 positions 按"文件索引降序"排序（`zone_encoder.cc:537-538`），对同一 target 等价于 timestamp 升序；`GetRangeLimit` 不重新排序就截断前 N 条（`lsm_engine.cc:590-598`）→ 可能拿到最旧的 N 条而不是最新。
- **Reader 关闭后状态不复位**：`Close()` 不清 `bloom_filter_`/`restart_points_`/decoders，复用同一个 Reader 打开另一个文件会残留旧状态（当前无复用调用方，属 API 缺陷）。
- **ODR 隐患**：`temporal_storage_layer.cc` 在 namespace cedar 内重新定义了 `struct Timestamp`，与 `cedar_key.h` 的 `class Timestamp` 同名不同定义；链接器通常不报错，但这是未定义行为，LTO/ABI 场景有风险（子审计标记，未编译验证）。

### 10.11 建议补进第 6 节的回归实验

8. **单行文件**：写 1 条属性 → flush → 点查/时间查询/重启后读回；预期当前全部失败（10.1）。
9. **删除 + 重启**：Put → Delete → flush → 关闭重开 → Get；预期旧值复活（3.2）。
10. **批量边**：`WriteBatch` 写两条同 src/type、不同 dst 的边 → 提交 → 读回 dst；预期都是 dst=0 或被覆盖（8.1）。
11. **损坏文件**：截断文件尾/改 header 的 zone_maps_offset → Open/查询；预期越界读或崩溃（10.5）。
12. **并发 GetRange**：16 线程共享 `SstReaderCache` 查询同几个文件 → 预期数据竞争/缓存自旋（10.8）。
