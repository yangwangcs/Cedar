- 依据：docs/audit/0.1-storage-audit-2026-10-22.md（三轮审计，11 个 P0）

## 1. 背景与问题定性

0.1 是"版本链跳表 + 自研列式 SST + Size-Tiered 合并"的原型。审计确认它不是零散 bug，而是三条契约链断裂：

1. 写入不可信：先 memtable 后 WAL、无 replay、flush 丢墓碑、flush 失败仍销毁 imm_。
2. 键语义不统一：target_id 没贯穿 key→memtable→SST→查询 API；entity_type/sequence 不参与跳表排序；SST 不持久化 txn_version。
3. 合并不可开启：混合列/类型合并、重叠文件未合并即删除、双文件号分配器、三套执行者无任务预留。

同时存在"格式写了但不用"的性能浪费：Bloom 从未分配、Entity Index 两端禁用、restart point/zone map 无读者、target 解码 O(n²)、每个 reader 整文件入内存、32 路合并 O(N×K)。

## 2. 目标与非目标

### 2.1 目标

- 正确性：11 个 P0 全部修复并有回归测试；删除、边、恢复、并发四类语义可信。
- 性能（单机、同硬件、同 workload 对比基线）：
  - VSL 8 线程插入吞吐 ≥3x；
  - SST 点读 p99 ≥5x，打开 100MB SST 峰值 RSS −50%；
  - 32 路合并吞吐 ≥5x，flush 吞吐 ≥1.25x；
  - 大文件全量扫描从 O(n²) 降到 O(n)。
- 可维护：一个比较器、一个文件号分配器、一套 levels 权威、一个调度器。

### 2.2 非目标（明确不做）

- 不改 CedarKey 的 32B 布局、字段偏移、Encode/Decode、~timestamp 降序编码。
- 不改 Zone-Columnar v1 的文件布局（Header 256B/Footer 128B/5 Zone/ZoneMap 32B/RestartPoint 16B），不升版本。
- 不把 Size-Tiered 换成 Leveled/Tiered 混合，不引入 RocksDB/LevelDB。
- 不移植 main 的 FactRef/位时模型（那是另一条产品线）。
- 不引入新第三方依赖，不改变公开 API 的既有签名（只新增重载）。

### 2.3 设计不变量（任何优化不得破坏）

| 不变量 | 约束 |
|---|---|
| Key | CedarKey 32B；entity/type/column/target/ts/seq/flags 语义不变 |
| SST 格式 | v1 五区布局与字段尺寸不变；新写法通过 header.flags 保留位区分，读端兼容旧文件 |
| LSM 模型 | 单 WAL、Size-Tiered L0–L6、容量触发、单 Manifest 权威 |
| API | 既有签名保留；新增 target_id 重载与错误返回 |
| 依赖 | C++17 + 现有 gtest/lz4/protobuf/gRPC |

## 3. 总体设计

### 3.1 分层与职责

    [事务层]  OCC + WriteBatch + WAL
         |  commit_seq / 写集
    [MemTable] LockFreeVSL（版本链）+ arena
         |  flush（按 entity_type,column 分组，含墓碑）
    [L0..L6]  SizeTieredCompactionEngine（唯一 levels + manifest 权威）
         |  k-way merge / 输出切分 / 原子安装
    [SST]     Zone-Columnar v1（5 zone + block 索引 + bloom/entity index）
         |  mmap reader + reader cache + file index
    [查询]    Get/GetAtTime/GetRange/Scan（完整 key，target 贯穿）

### 3.2 三条主线

主线 A：可信写入链路
WAL-first → memtable → flush（含墓碑）→ compaction（inputs∪overlaps）→ manifest 提交 → 删除旧文件。
任何一步失败都不得销毁唯一副本；恢复时 WAL 重放补齐。

主线 B：统一键语义
一个比较器（CedarKey::Compare）贯穿 VSL、flush、compaction、reader；target_id 从 key 到 API 全链路传递；SST 行重建使用 header + zone2 + zone3 的完整信息。

主线 C：分层读路径
memtable → imm → SST；SST 读取统一走 mmap view + reader cache + 每 (type,column) 文件区间索引；多文件结果用 K 路归并，不拼接后全排序。

### 3.3 关键设计决策

D1 单一元数据权威：SizeTieredCompactionEngine 的 levels_ + MANIFEST-zc 是唯一事实来源。LsmEngine::levels_ 改为只读缓存（或删除），flush/compaction 都通过同一接口更新；checkpoint 从权威源生成。
理由：现状两套 levels 不同步，checkpoint 漏压缩输出、查询读已删文件。

D2 单一文件号分配器：FileNumberAllocator 由 LsmEngine 持有，压缩引擎通过引用使用；每次分配持久化到 manifest。任何路径不得复用已存在文件号，写文件前做存在性检查。
理由：现有双计数器在第一次压缩后必撞号，覆盖压缩输出。

D3 MemTable 生命周期：memtable 用 shared_ptr 管理；事务/读在操作期间持有引用；ForceFlush 失败保留 imm_；旧表在所有读者释放后回收（引用计数或 epoch）。
理由：裸指针 UAF 与并发 flush 丢写是当前最高危问题。

D4 WAL-first 与重放：Commit 先写 WAL（含 commit 记录）再写 memtable；Open 时按 WAL 顺序重放，未提交事务不落表；重放幂等（key+txn_version 去重）。
理由：当前"提交成功"不等于可恢复，且普通 Put 不进 WAL。

D5 格式兼容策略：写端修正（单行时间戳、target 文件级编码、CRC），读端通过 header.flags 与新解码器兼容旧文件；不提升版本号。旧文件 fixture 必须进测试。
理由：不能牺牲已有数据；也不能因修 bug 强制迁移。

D6 并发策略：VSL 实现真正的 CAS 插入（兑现 LockFree 设计）；reclamation 靠 memtable 生命周期（arena 整块释放，不做节点级回收），避免 ABA；reader 视为不可变对象，索引在 Open 时或 once_flag 下构建。
理由：既要并发性能，也要避免引入 hazard pointer 复杂度与 UAF。

## 4. 子系统设计

### 4.1 持久化与事务

- Commit 顺序：validate → 分配 commit_seq → WAL（put/delete + commit）→ fsync（按策略）→ memtable（带 commit_seq）→ 返回成功。
- 恢复：LoadSstFiles → 读 MANIFEST 恢复层级 → WAL replay（按 txn 边界）→ 重新构建 memtable → 接受写。
- 删除：统一用 Descriptor::Tombstone 作为持久化表示；flush 写出墓碑；读路径遇墓碑返回 not-found；compaction 在 bottommost 且无读快照依赖时才清理（Phase 4 实现，之前保持 false）。
- flush 生命周期：失败保留 imm_ 并返回可重试错误；Close 传播错误；自动切换按 ApproximateMemoryUsage()（字节）而非条目数。
- MVCC：txn_version 统一由事务管理器分配 commit_seq；读可见性用 commit_seq <= snapshot_seq；SST 持久化 commit_seq（可通过 CedarKey 的 sequence 扩展或新增 zone 字段，需在 Phase 1 定方案；若坚持不改 key，则 flush 时把 commit_seq 写入 KeyMetadata zone 的保留位/新增 zone）。
  说明：这是唯一可能需要"扩展格式字段"的点；优先方案是复用 Zone3 的 flags/sequence 保留位，若不足则用 header.flags 标明扩展，不改既有字段语义。

### 4.2 版本链跳表

- 插入：标准无锁跳表算法——从最高层找前驱，逐层 CASNext；失败重找；节点 next 指针先填后发布；version chain 的 older 在发布前设置，newer 用 CAS 回链（当前 newer 未使用，可先删除字段）。
- 排序：跳表比较必须与 CedarKey::Compare 完全一致（entity → entity_type → column → target → timestamp → sequence → flags）；现有"entity, column, target, ts"排序是历史版本链断裂的直接原因。
- 分配：MemTableArena 按 1MB slab 分配 LFNode，memtable 析构整块释放；消除 per-node malloc/free 与内存碎片。
- 扫描：Traverse 使用模板/function_ref；GetKey 延迟构造；ScanRange 直接返回视图/预留容量，去掉三层 vector 拷贝。
- 批量：PutBatch 一次定位、一次链入，供 WAL replay 与批量导入。
- 读优化：GetAtTime 先用 encoded timestamp 比较；版本链只在同一 user key 内遍历；target 必须参与定位。

### 4.3 列式存储

写端：
- 单行时间戳：Decoder 构造时无条件把 first_ts 放入 cache（修复 10.1）。
- target zone：改为文件级一次编码（收集后 Finish 统一 Encode），去掉每 block 的 1B tag；header.flags 标记新写法；旧文件按旧路径解码。
- Encoding type 写入 header；kDelta 要么实现完整差分解码，要么写端禁用。
- Bloom：Finish 前按 num_entries 初始化，写入真实 num_keys；Entity Index：启用 Write/Load（字段已存在）。
- CRC：对 header 与 data 计算并校验（格式字段已存在，不新增布局）。
- Blob：写端 fsync 顺序、size_kb 上限校验；读端修正二次剥离；compaction 重写 blob 或引用计数（Phase 3 收口）。

读端：
- mmap/zero-copy：Open 映射文件，zone 用 Slice 视图，decoder 接受视图，避免整文件复制多份。
- 块偏移表：每 8192 行记录 (byte_offset,row_idx)，一次线性扫描构建；Get/FindTimeRange 用块表二分，块内解码 ≤8192 行。
- target：一次性展开为 vector<uint64_t>（O(n) 内存），消除 O(n²)；value 固定 kRaw 时按 idx*8 直接索引。
- 完整 key 重建：ReconstructKey(row, header) 使用 entity+type+column+target+ts+seq+flags。
- reader cache：按 file_number 缓存，修复淘汰死循环；所有读路径统一使用。
- 文件区间索引：每 (type,column) 按 min_entity 排序，查询 O(log F) 选文件。
- 多文件结果：K 路归并（完整 key），limit 在归并中截断；删除 10 文件静默上限。

### 4.4 LSM 合并

- 任务模型：PickNextCompaction 按 (entity_type,column) 分组；任务输入 = 同组 L0/Ln 文件 + L(n+1) 重叠文件；返回任务时原子登记 reserved_files_。
- 合并：K 路堆（CedarKey::Compare）；同 key 规则：ts 相同取 sequence 更大；完全相等保留文件号更大的；输出按 l0_file_size 切分。
- 安装：输出写 tmp → fsync → 原子 rename；manifest 更新（fsync+rename+dir fsync）；先提交元数据再删除输入；失败保留输入、清理输出。
- 调度：只保留一个调度器（engine worker），删除 AutoCompactionThread 直接执行；失败指数退避；pending 有界；enable_background_compaction 真正生效。
- Flush：向量分组替代 std::map；原地排序；reserve；禁用时不构建 entity index；墓碑保留。
- 统计：按字节累加，输出 meta 的真实 min/max。

### 4.5 读路径

- 统一入口：Get/GetAtTime/GetAll/GetRange/GetRangeLimit/BatchGetRange 都走 reader cache + 文件索引 + 完整 key 比较。
- 错误语义：损坏/打开失败不得静默 continue；返回 Corruption 或 incomplete 标志。
- 墓碑：读路径统一过滤。
- 结果顺序：最新优先；limit 先归并后截断。

## 5. 性能模型与目标

| 热点（现状） | 成本 | 优化 | 目标 |
|---|---|---|---|
| VSL 每节点 new/delete + 非 CAS 插入 | 分配/缓存不友好/并发崩溃 | arena + CAS | 8 线程 ≥3x，0 per-node malloc |
| 每 reader 整文件读入 + 多份 zone 复制 | 内存 3–4x 文件大小 | mmap + Slice 视图 | 100MB SST RSS −50% |
| target 解码每行从头扫描 | O(n²) | 一次展开/块表 | 扫描 ≥10x |
| 32 路合并线性找最小 | O(N×K) | K 路堆 | ≥5x |
| Bloom/Entity Index/restart/zone map 全未用 | 每次点查扫 entity zone | 启用索引 | 不存在 entity 跳过 ≥90% |
| 每 (type,column) 一文件 + 10 文件上限 | 文件数爆炸/漏查 | 文件区间索引 + 完整归并 | O(log F)，结果完整 |
| flush 用 std::map + 整份复制 | 常数大/临时内存高 | 向量分组+原地排序 | 吞吐 ≥1.25x，内存 −30% |

测量：benchmarks/storage_bench（JSON），单线程/8 线程，1 万/10 万/100 万行，记录 p50/p99/吞吐/RSS；每任务前后对比，>5% 回归即失败。

## 10. Blob 设计补全（T11，用户追加范围）

### 10.1 现状与问题

SST 本地 Blob 路径当前没有生产者（AddValue 无调用者），但代码里存在三个必须补齐的缺陷：
1. 读端二次剥离：BlobFileReader::Read 已消费 4B 长度前缀，SimpleSSTBlobManager::ReadBlob 又把 payload 前 4B 当长度（zone_columnar_format.cc:81-92 + blob_file.cc:314-333）。
2. 写端静默降级：AddValue 对 5~6 字节值调用 InlineShortStr（上限 4B）失败后写 Descriptor()（Tombstone）；Blob 打开/写入失败同样静默 Tombstone。
3. 生命周期断裂：compaction 只拷贝 BlobRef 指针，输出 SST 却按新的 sst_<n>.blob 解析；输出 meta 不登记 blob_file_number，引用计数/GC 不知道依赖；reader 也没有 db_path（全仓库无 SetDbPath 调用）。

### 10.2 设计决策

- 存储单元：每个 SST 拥有一个 sst_<file_number>.blob；entry = [4B payload 长度][payload]，4KB 页对齐；沿用现有命名与 Descriptor::BlobRef(offset,size_kb,checksum)。
- 内联阈值：value.size() <= 4 内联；4 < size <= 60MB 走 Blob；>60MB 返回 InvalidArgument（size_kb 是 uint16，64MB 会溢出；本任务不改 Descriptor 布局，因此显式设上限）。
- 写入顺序：Blob 追加 → Blob Sync → SST Sync（SST 是提交点）；SST 失败时 GC 回收孤儿 blob。
- 读取：Reader 构造必须拿到 db_path（构造函数参数或从 SST 路径推导，禁止依赖调用方记得 SetDbPath）；ReadBlob 修正为直接使用 Read 返回值；校验长度、checksum、页对齐；GetValues 在 db_path 缺失/Blob 缺失时返回错误，不再静默空串。
- Compaction：对输入中的 BlobRef 一律重写到输出 sst_<new>.blob（大值可后续优化为共享 + 引用计数），输出 meta 填 blob_file_number/blob_file_size；失败保留输入；成功提交 MANIFEST 后再删旧 blob。
- GC：BlobReferenceManager 的引用计数随 MANIFEST 持久化；启动时清理无引用 blob；TriggerBlobGC 接入压缩/关闭路径。
- 边界：auto_blob_storage 的全局 BlobFileManager 是另一套子系统，本任务不改，只在文档中说明两者边界。

### 10.3 验收

- 大值 roundtrip（5B、1MB、接近 60MB）、64MB 以上拒绝、损坏/截断 blob 返回错误。
- AddValue 任何失败都不得写 Tombstone（返回 Status）。
- compaction 后大值可读，旧 blob 在无引用后删除，重开后仍可读。
- 崩溃注入：Blob 写失败/SST 写失败/压缩中断不产生悬空引用，输入数据不丢。



### 10.4 补充：flush 非 fsync 与 WAL 截断的顺序约束（t7/t10 决策）

t7 在 WAL 开启时把 flush SST 的 Sync 降级为 Flush，换取 flush 2.6x 吞吐。该优化成立的前提是 WAL 仍保存着可重放的记录。一旦 t10 引入 WAL 截断，必须满足：

1. 截断前先 fsync 水位内所有 SST（文件 + 目录）并持久化 MANIFEST；
2. 只删除水位之前的 WAL 段，绝不先删 WAL 再等 SST 落盘；
3. 崩溃注入覆盖“flush 成功、SST 未 fsync、WAL 尚未截断”与“截断进行中”两个窗口；
4. 若顺序无法保证，回退为 flush 每文件 fsync，接受吞吐损失。

该约束与“WAL 是唯一可恢复副本”的主线 A 一致，必须在 t10 的验收里体现。
